## Read this before comparing these rows to anything

**This is a llama.cpp box, not an LM Studio box.** Every row here came from
`llama-server` out of the `fiveforge/llama.cpp` fork (branch `wp-g2`), driven by
`defiant/harness/qwen36_v100.py` rather than `bench.py`. Full method, provenance and
analysis: `defiant/benchmarks/2026-08-14-v100-qwen36-256k.md`.

**Do not compare against `e5-2680-cpuonly-63g-b105`.** Same chassis, but that id predates
the second CPU, the RAM upgrade *and* the GPU — it is single-socket, 63 GB, CPU-only.

**Every row is at the full native 262,144 context**, allocated at load. VRAM does not move
with depth (28,958 MiB at every depth in the champion config), so "256K resident" is a
property of all of these rows, not just the deep ones.

| `mtp-ub2048` / `nomtp-ub2048` | the MTP A/B — **both** arms at `-ub 2048`, because MTP does not fit at 4096 |

All arms run `GGML_CUDA_DISABLE_GRAPHS=1 GGML_CUDA_VOLTA_MOE_MMQ=1`, flash-attention on,
f16 KV, greedy sampling.

## The three things worth knowing

1. **`-ub` is the single biggest lever on this model and the default is wrong for it.**
   512 → 4096 is worth **+100.8% prefill at 4K** and **+36.3% at the full 257,744**, with
   decode unchanged. With 256 experts and 8 routed per token, a 512-token micro-batch
   already touches nearly every expert, so the weight reads amortise over 8× more tokens
   at 4096. `GGML_CUDA_VOLTA_MOE_MMQ` is worth **+117%** at a wide micro-batch versus the
   +64% previously recorded at the narrow one — **neither flag should be quoted without
   the other.**

2. **Decode is at the memory-bandwidth wall, and the wall is computable.** At 257,744
   tokens each decoded token reads 7,664 MiB (2,624 MiB of weights + 5,040 MiB of f16 KV).
   Against the 964.8 GB/s this card actually achieves, that is a **120.1 tok/s ceiling**.
   Measured 62.92 is **52% of roofline**. A 150 tok/s target is outside this card's physics
   at f16 KV.

3. **Concurrency at full 256K is exactly one stream.** `-np` splits `-c` across slots, so
   `-np 8 -c 262144` is eight 32K streams, not eight 256K streams. Two streams at the full
   context (`-np 2 -c 524288`) OOMs at load on the compute buffer. Even at shallow depth,
   aggregate throughput saturates at **two** streams; beyond that it buys nothing and
   fairness falls to 0.276 by eight.

## Recommended config

```sh
GGML_CUDA_DISABLE_GRAPHS=1 GGML_CUDA_VOLTA_MOE_MMQ=1 \
  llama-server -m Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf \
  -ngl 99 -c 262144 -np 1 -ub 4096 -b 8192
```

`GGML_CUDA_DISABLE_GRAPHS=1` is a crash workaround. The old note that it is "free because
graphs never engage" was measured on this MoE with the env set in every arm and is **wrong
for Qwen3.8-27B**: there, graphs DO engage and then crash (the fork's q8_1 dedup arena
relocates on growth, invalidating captured-graph pointers — see
`defiant/benchmarks/2026-08-17-v100-qwen38-session3.md`). The env is **load-bearing** on
the dense hybrid; graphs measured flat-to-negative even when made to work (36.11 vs 36.61). Add `--spec-type draft-mtp --spec-draft-n-max 3` **with
`-ub 2048`** for +29% decode at 256K, at the cost of −9.7% prefill, +86% TTFT and 2.8× the
P95 inter-token latency — and only at 1–2 concurrent streams, since MTP goes negative at 4+.


## Qwen3.8-27B session-3 labels (2026-08-17/18)

| label | what it is |
|---|---|
| `q38-s3-composite-u4` | session-2 composite reproduced under the production 262,144-ctx server (RPB2 + NWARPS2 + norm-quant fusion + FATTN_VEC_KV_UNROLL=4) |
| `q38-s3-mtp4` | composite + `--spec-type draft-mtp --spec-draft-n-max 4 -ub 2048` — target-verified exact, accept 59%, VRAM 30,742 MiB |
| `q38-s3-ngram-mod` | composite + `--spec-type ngram-mod` — context n-gram speculation, no draft model, output byte-identical, zero VRAM/prefill cost |

The prompt_tokens=1065 rows are the shallow production benchmark (128-token windows,
medians of 3, warmup discarded). Speculative rates are prompt-dependent: ngram-mod
measured 54.9 on the standard bench prompt, 59.0 over 512 novel-fiction tokens, and
117–125 on note-review prompts whose answers quote the source; MTP n=4 spans 44.2–51.8
across the same prompts. Single-token (no-spec) decode is prompt-invariant at ~36.5,
which is 77% of the ~47 t/s bandwidth+tail ceiling — session 3 closed every remaining
single-token kernel idea as measured-negative (shape-routed rpb, K-loop unroll,
register caps, verify-path geometry, CUDA graphs). Full record:
`defiant/benchmarks/2026-08-17-v100-qwen38-session3.md`.

### Recommended configs (qwen3.8-27b, 1x V100 32GB, full 256K resident)

Build flags: `-DGGML_CUDA_MMVQ_DENSE_RPB=2 -DGGML_CUDA_MMVQ_DENSE_NWARPS=2 -DGGML_CUDA_FATTN_VEC_KV_UNROLL=4`
Env: `GGML_CUDA_DISABLE_GRAPHS=1 GGML_CUDA_FATTN_VEC_GQA=2 GGML_CUDA_FUSE_NORM_QUANT=1`

```sh
# throughput-first (repetitive/agentic/log/code workloads; byte-identical output):
llama-server -m Qwen3.8-27B-UD-Q4_K_XL.gguf -ngl 99 -c 262144 -np 1 -ub 4096 -b 8192 \
  -fa on -ctk q8_0 -ctv q8_0 --ctx-checkpoints 0 --spec-type ngram-mod

# balanced (novel free-form text; exact, +1.7 GiB VRAM, -4% prefill):
llama-server ... -ub 2048 --spec-type draft-mtp --spec-draft-n-max 4
```

UPDATE 2026-08-18: the combined abort was VRAM OOM from uncapped ngram verify
batches, not a logic bug. With `--spec-ngram-mod-n-max` capped (24 optimal, ≤32 max)
the combination works and is the new champion (`q38-s3-mtp2-ngram24`):

```sh
# champion — warmed steady state 110.6 t/s @1K (cold single request ~46):
llama-server ... -ub 2048 --spec-type draft-mtp,ngram-mod \
  --spec-draft-n-max 2 --spec-ngram-mod-n-max 24
```

The ngram table persists per server instance and warms over requests: 45.6 → ~70 →
110+ flat from request 3. Never run the combination UNCAPPED — it OOMs at 256K.
