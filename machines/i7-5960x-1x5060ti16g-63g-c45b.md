## Notes

This is **DeV-LSi** — the box formerly benched as `i7-5960x-1x10708g-63g-16b2` (GTX 1070), now
carrying a single **RTX 5060 Ti 16 GB**. New id because the GPU changed. CachyOS (Linux), single
1440p display. Reachable over the tailnet; driven remotely via `lms --host dev-lsi` and
`LMS_HOST=http://dev-lsi:1234 python3 bench.py ...`.

Target role: **Hindsight** agent host — parallel agentic streams, full native context.

## The one thing that matters: LM Studio's auto offload ratio silently spills to CPU

Out of the box, `openai/gpt-oss-20b` (MXFP4, 11.28 GiB) loads with **~2 GB of VRAM left free**
while expert layers run on the CPU. The tell is not a load error — it's the *shape* of the
telemetry:

| | default load | `offload=1.0`, flash on, KV q8_0 |
|---|---:|---:|
| GPU utilization | 40–45 % | **75–77 %** |
| GPU power | 76 W | **120 W** |
| host CPU | ~25 % of 16 threads (≈4 pegged) | **~6.8 %** |
| decode, 1 stream | 57.5 tok/s | **96.3 tok/s** |

Fixing it is worth **+67 % single-stream and +81 % aggregate at 8 streams**, at *full 131k context*.

**A flat context curve is not proof of residency.** Decode measured 57.1 / 56.7 / 57.6 / 57.5 tok/s
at 16k / 32k / 64k / 131k — perfectly flat, which reads like "context is free" but actually meant
"the CPU spill dominates at every context, so context is irrelevant." Always confirm with GPU
util + host CPU, not with a speed-vs-context curve.

## KV cache is UNIFIED — context is a shared pool, not per-agent

`srv load_model: n_slots = 16, n_ctx_slot = 131072, kv_unified = 'true'`. VRAM is essentially
identical at parallel 4 / 8 / 16 (13892 vs 13903 MiB), which proves `n_ctx` is allocated **once**
and shared. 16 agents do **not** get 131k each — they share 131,072 tokens total (~8k average).
Size `-c` against *aggregate* demand across concurrent agents.

|---|---:|---:|---:|
| q8_0 | 96.3 | 185.1 | 1975 MiB |

f16 is ~3 % faster and higher quality, but leaves only ~700 MiB of headroom. q8_0 is the safer
default on a box that also drives a display; f16 is fine if this stays dedicated.

## Use the native MXFP4, not a Q8 "upcast"

gpt-oss ships natively in MXFP4. `lmstudio-community/gpt-oss-20b-GGUF` MXFP4 is **11.28 GiB**;
unsloth's `UD-Q8_K_XL` is **12.29 GiB** — ~1 GiB larger for no quality gain, since it upcasts
already-4-bit expert weights. On a 16 GB card that gigabyte is the difference between comfort
and spilling.

## Linux display overhead is a real advantage

Idle VRAM with no model loaded: **720 MiB** (CachyOS, one 1440p display). The Windows 9800X3D box
with 3×4K desktops sits at **~2400 MiB**. That ~1.7 GB delta is decisive at this model size — the
Windows box could not hold gpt-oss-20b Q8_K_XL resident at any useful context, while this box
holds MXFP4 at the full 131k with room to spare.

Platform caveat: PCIe reports **gen1 x8** (gen3 x16 max) on this aging X99 board, and the 5960X is
slow by modern standards. Neither matters much once the model is fully resident, but both punish
any spill hard — another reason to verify residency here rather than assume it. Prefill numbers on
5960X hardware have historically been cache-tainted; treat prefill rows from this box with care.

## Model comparison for a concurrent agentic workload (2026-08-01/02)

Choosing a model for a concurrent agentic workload on this box — many short structured
requests rather than one long chat. Decode throughput under concurrency is the metric that
matters, and it ranks models differently from single-stream.

| | E4B (3.9G) | 12B-QAT (6.7G) | 26B-A4B (12.7G) | gpt-oss-20b (12.1G) | Qwen3.5-9B (10.5G) |
|---|---:|---:|---:|---:|---:|
| decode c=1 | 78.7 | 49.7 | 68.8 | **96.3** | 39.5 |
| agg c=8 | 184.4 | **232.1** | 152.8 | 185.1 | 136.2 |
| agg c=16 | 205.5 | **364.7** | n/a | 225.7 | — |
| max ctx | 131k | 131k | **32k only** | 131k | 131k |
| free VRAM | **10.5G** | 3.6G | 0.5G | 2.0G | 2.5G |

### Dense beats MoE on aggregate — the opposite of the usual intuition

Only the **fully dense** 12B amortizes one weight read across a whole batch. E4B
(MatFormer selective activation), 26B-A4B (MoE) and gpt-oss (MoE) all have concurrent
streams touching *different* sub-networks, so they scale worse under load even when they
win single-stream. gpt-oss is fastest at c=1 (96.3) yet the 12B beats it by **62%** at 16
streams (364.7 vs 225.7). **Never pick a model for a concurrent workload on a
single-stream benchmark.**

### Verbosity × speed is a real disqualifier

Long single generations race any client-side timeout. `gemma-4-12b-qat` needed ~5563
completion tokens where `gpt-oss` used ~825–938 for equivalent work; at 49.7 tok/s that is
~112 s, enough to blow a 120 s timeout. Token efficiency matters as much as tok/s when a
caller imposes a deadline.

### Harness traps that produced wrong answers before being caught

- **Strip think tags.** A probe scoring 0/10 *both with and without* `json_schema` is a
  broken harness, not a broken model — that symmetry is the tell. Production clients
  typically strip `<think>/<thinking>/<thought>/<reasoning>`; a naive probe stripping only
  markdown fences scores every thinking model at zero.
- **Check `finish_reason=length` before blaming a model.** Both Gemmas scored 0/5 on a
  long-generation task purely because the harness capped output at 2500 tokens.
- **Normalise Unicode before token matching.** Some models emit U+2011 hyphens and U+00A0
  spaces; ASCII patterns then report failures for checks the model actually passed.
- Qwen3.5-9B's failure is real and different: it spends the whole budget reasoning
  (2000/2000 tokens, **empty** content; needs 2760 to answer at all, 771 with
  `/no_think`). A thinking model is a poor fit for per-turn extraction.

## Real-world load: structured output moves the bottleneck OFF the GPU

Ran a genuine production workload on this box — classifying 12,450 short text records with
`gemma-4-E4B-it-qat`, 16 concurrent streams, every request using `response_format: json_schema`.
It behaves materially differently from the synthetic sweep.

| | synthetic bench | real classification load |
|---|---:|---:|
| aggregate @16 streams | 205.5 tok/s | **179 tok/s** (−13 %) |
| per-stream | 12.8 tok/s | 11.2 tok/s |
| GPU utilization | 76 %+ | **28–50 %** |
| GPU power | 120 W | **43–73 W** |
| prefill | — | 1057 tok/s aggregate, median 1337 tok/req |
| decode | — | median **2446 tok/req** |

**The GPU is not the limiter.** 179 tok/s while the card sits at ~40 % utilization and half the
power it drew during benchmarking. Two causes:

1. **Constrained decoding is CPU work.** Every token is validated against the compiled GBNF
   grammar, per stream, CPU-side. `lm-studio` (the orchestration process) held ~74 % of one core
   throughout while `llama-server` used only 8 % — the inverse of the CPU-spill signature.
   LM Studio also appears to compile the schema to GBNF **per request**, not once per schema.
2. **Output is mostly thinking, not answer.** Median 2446 output tokens per batch of 20 verdicts.
   The JSON itself is ~500 tokens; the rest is E4B reasoning. Capping the answer text barely moved
   throughput because thinking dominates the output budget.

**Implication:** the `parallel=16` optimum from the unconstrained sweep is probably NOT optimal for
structured-output workloads — with the GPU half-idle, more streams should fill the gaps. Worth a
dedicated sweep: same concurrency ladder with and without `response_format` to isolate grammar cost.
This is the first structured-output data in this repo; every prior row is unconstrained decode.

Throughput note: 16 workers took 124 min for 12,020 classifications; single-stream would have been
~4.7 h. Batching 20 facts per call also amortises the ~2500-token system prompt.

### It takes both crowns, which nothing else here has done

| | LFM2.5-2.6B | gpt-oss-20b | gemma-12B-QAT | gemma-E4B |
|---|---:|---:|---:|---:|
| decode c=1 | **109.2** | 96.3 | 49.7 | 78.7 |
| agg c=16 | **381.1** | 225.7 | 364.7 | 205.5 |
| size | **2.87 GB** | 12.11 GB | 7.15 GB | 4.22 GB |

Every previous model traded one axis for the other: gpt-oss won single-stream and lost 62 % at
16 streams; the dense 12B won aggregate and was slowest at c=1. LFM2.5 wins both, from a file a
quarter the size of gpt-oss.

That is consistent with the mechanism established earlier on this box: it is **dense**, so one
weight read amortises across the batch (good aggregate scaling), and it is **small**, so
bytes-read-per-token is low (good single-stream). Prior candidates had one property or the other,
never both. Prefill at 8,935 tok/s is also the highest recorded here — roughly 7× what gpt-oss
managed under real structured-output load (1,057 tok/s).

### Caveats

- Benched with `gemma-4-e4b-it-qat` **co-resident but idle** (deliberate). Compute was unaffected;
  VRAM was not — 6.4 GB free rather than ~9.3 GB solo. Decode/prefill numbers stand, but context
  headroom in these rows is understated.
- **Throughput says nothing about output quality.** A 2.6B model topping this table is a statement
  about bytes-per-token, not capability. Earlier extraction work on this box showed small models
  fabricating dates confidently while emitting perfectly valid JSON — measure quality separately
  before drawing any suitability conclusion.
- `lms get` cannot resolve this repo (`LiquidAI/LFM2.5-2.6B-GGUF`), same as the unsloth repos.
  Parallel byte-range curl is the working path; a single stream is throttled to ~1 MB/s.
