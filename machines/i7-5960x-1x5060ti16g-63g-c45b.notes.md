## The one thing that matters: LM Studio's auto offload ratio silently spills to CPU

Out of the box, `openai/gpt-oss-20b` (MXFP4, 11.28 GiB) loads with **~2 GB of VRAM left free**
while expert layers run on the CPU. The tell is not a load error — it's the *shape* of the
telemetry:

| | default load | `offload=1.0`, flash on, KV q8_0 |
|---|---:|---:|
| GPU utilization | 40–45 % | **75–77 %** |
| GPU power | 76 W | **120 W** |
| host CPU | ~25 % of 16 threads (≈4 pegged) | **~6.8 %** |
| decode, 1 stream | 57.5 tok/s | **96.3 tok/s** |

Fixing it is worth **+67 % single-stream and +81 % aggregate at 8 streams**, at *full 131k context*.

**A flat context curve is not proof of residency.** Decode measured 57.1 / 56.7 / 57.6 / 57.5 tok/s
at 16k / 32k / 64k / 131k — perfectly flat, which reads like "context is free" but actually meant
"the CPU spill dominates at every context, so context is irrelevant." Always confirm with GPU
util + host CPU, not with a speed-vs-context curve.

## gpt-oss-20b, MXFP4, 131k ctx, flash on, KV q8_0, threads 8, offload 1.0

| parallel slots | streams | per-stream | aggregate |
|---:|---:|---:|---:|
| 8 | 1 | 96.3 | 96.3 |
| 8 | 2 | 62.9 | 125.7 |
| 8 | 4 | 40.7 | 162.9 |
| 8 | 8 | 23.1 | 185.1 |
| 16 | 8 | 22.5 | 179.9 |
| 16 | 12 | 17.6 | 211.8 |
| 16 | 16 | 14.1 | **225.7** |

Aggregate keeps climbing to 16 streams; per-stream falls below ~15 tok/s there, so pick the slot
count from whether you care about latency or total throughput. Note `parallel=16` is slightly
*worse* than `parallel=8` at 8 streams (179.9 vs 185.1) — don't over-provision slots.

## KV cache is UNIFIED — context is a shared pool, not per-agent

`srv load_model: n_slots = 16, n_ctx_slot = 131072, kv_unified = 'true'`. VRAM is essentially
identical at parallel 4 / 8 / 16 (13892 vs 13903 MiB), which proves `n_ctx` is allocated **once**
and shared. 16 agents do **not** get 131k each — they share 131,072 tokens total (~8k average).
Size `-c` against *aggregate* demand across concurrent agents.

## KV quant: q8_0 vs f16 at 131k

| KV | decode c=1 | agg c=8 | VRAM free |
|---|---:|---:|---:|
| q8_0 | 96.3 | 185.1 | 1975 MiB |
| f16 | 99.5 | 186.8 | **719 MiB** |

f16 is ~3 % faster and higher quality, but leaves only ~700 MiB of headroom. q8_0 is the safer
default on a box that also drives a display; f16 is fine if this stays dedicated.

## Use the native MXFP4, not a Q8 "upcast"

gpt-oss ships natively in MXFP4. `lmstudio-community/gpt-oss-20b-GGUF` MXFP4 is **11.28 GiB**;
unsloth's `UD-Q8_K_XL` is **12.29 GiB** — ~1 GiB larger for no quality gain, since it upcasts
already-4-bit expert weights. On a 16 GB card that gigabyte is the difference between comfort
and spilling.

## Linux display overhead is a real advantage

Idle VRAM with no model loaded: **720 MiB** (CachyOS, one 1440p display). The Windows 9800X3D box
with 3×4K desktops sits at **~2400 MiB**. That ~1.7 GB delta is decisive at this model size — the
Windows box could not hold gpt-oss-20b Q8_K_XL resident at any useful context, while this box
holds MXFP4 at the full 131k with room to spare.

Platform caveat: PCIe reports **gen1 x8** (gen3 x16 max) on this aging X99 board, and the 5960X is
slow by modern standards. Neither matters much once the model is fully resident, but both punish
any spill hard — another reason to verify residency here rather than assume it. Prefill numbers on
5960X hardware have historically been cache-tainted; treat prefill rows from this box with care.
