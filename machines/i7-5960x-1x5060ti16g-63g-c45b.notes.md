This is **DeV-LSi** — the box formerly benched as `i7-5960x-1x10708g-63g-16b2` (GTX 1070), now
carrying a single **RTX 5060 Ti 16 GB**. New id because the GPU changed. CachyOS (Linux), single
1440p display. Reachable over the tailnet; driven remotely via `lms --host dev-lsi` and
`LMS_HOST=http://dev-lsi:1234 python3 bench.py ...`.

Target role: **Hindsight** agent host — parallel agentic streams, full native context.

## The one thing that matters: LM Studio's auto offload ratio silently spills to CPU

Out of the box, `openai/gpt-oss-20b` (MXFP4, 11.28 GiB) loads with **~2 GB of VRAM left free**
while expert layers run on the CPU. The tell is not a load error — it's the *shape* of the
telemetry:

| | default load | `offload=1.0`, flash on, KV q8_0 |
|---|---:|---:|
| GPU utilization | 40–45 % | **75–77 %** |
| GPU power | 76 W | **120 W** |
| host CPU | ~25 % of 16 threads (≈4 pegged) | **~6.8 %** |
| decode, 1 stream | 57.5 tok/s | **96.3 tok/s** |

Fixing it is worth **+67 % single-stream and +81 % aggregate at 8 streams**, at *full 131k context*.

**A flat context curve is not proof of residency.** Decode measured 57.1 / 56.7 / 57.6 / 57.5 tok/s
at 16k / 32k / 64k / 131k — perfectly flat, which reads like "context is free" but actually meant
"the CPU spill dominates at every context, so context is irrelevant." Always confirm with GPU
util + host CPU, not with a speed-vs-context curve.

## gpt-oss-20b, MXFP4, 131k ctx, flash on, KV q8_0, threads 8, offload 1.0

| parallel slots | streams | per-stream | aggregate |
|---:|---:|---:|---:|
| 8 | 1 | 96.3 | 96.3 |
| 8 | 2 | 62.9 | 125.7 |
| 8 | 4 | 40.7 | 162.9 |
| 8 | 8 | 23.1 | 185.1 |
| 16 | 8 | 22.5 | 179.9 |
| 16 | 12 | 17.6 | 211.8 |
| 16 | 16 | 14.1 | **225.7** |

Aggregate keeps climbing to 16 streams; per-stream falls below ~15 tok/s there, so pick the slot
count from whether you care about latency or total throughput. Note `parallel=16` is slightly
*worse* than `parallel=8` at 8 streams (179.9 vs 185.1) — don't over-provision slots.

## KV cache is UNIFIED — context is a shared pool, not per-agent

`srv load_model: n_slots = 16, n_ctx_slot = 131072, kv_unified = 'true'`. VRAM is essentially
identical at parallel 4 / 8 / 16 (13892 vs 13903 MiB), which proves `n_ctx` is allocated **once**
and shared. 16 agents do **not** get 131k each — they share 131,072 tokens total (~8k average).
Size `-c` against *aggregate* demand across concurrent agents.

## KV quant: q8_0 vs f16 at 131k

| KV | decode c=1 | agg c=8 | VRAM free |
|---|---:|---:|---:|
| q8_0 | 96.3 | 185.1 | 1975 MiB |
| f16 | 99.5 | 186.8 | **719 MiB** |

f16 is ~3 % faster and higher quality, but leaves only ~700 MiB of headroom. q8_0 is the safer
default on a box that also drives a display; f16 is fine if this stays dedicated.

## Use the native MXFP4, not a Q8 "upcast"

gpt-oss ships natively in MXFP4. `lmstudio-community/gpt-oss-20b-GGUF` MXFP4 is **11.28 GiB**;
unsloth's `UD-Q8_K_XL` is **12.29 GiB** — ~1 GiB larger for no quality gain, since it upcasts
already-4-bit expert weights. On a 16 GB card that gigabyte is the difference between comfort
and spilling.

## Linux display overhead is a real advantage

Idle VRAM with no model loaded: **720 MiB** (CachyOS, one 1440p display). The Windows 9800X3D box
with 3×4K desktops sits at **~2400 MiB**. That ~1.7 GB delta is decisive at this model size — the
Windows box could not hold gpt-oss-20b Q8_K_XL resident at any useful context, while this box
holds MXFP4 at the full 131k with room to spare.

Platform caveat: PCIe reports **gen1 x8** (gen3 x16 max) on this aging X99 board, and the 5960X is
slow by modern standards. Neither matters much once the model is fully resident, but both punish
any spill hard — another reason to verify residency here rather than assume it. Prefill numbers on
5960X hardware have historically been cache-tainted; treat prefill rows from this box with care.

## Hindsight model bakeoff (2026-08-01/02)

Picking a model for Hindsight (agentic memory: fact extraction every turn, plus
periodic consolidation). Two metrics matter, and they disagree — decode throughput
*and* structured-output reliability measured through **Hindsight's own provider class**
(`OpenAICompatibleLLM`, `max_retries=0`), not a hand-rolled probe.

| | E4B (3.9G) | 12B-QAT (6.7G) | 26B-A4B (12.7G) | gpt-oss-20b (12.1G) | Qwen3.5-9B (10.5G) |
|---|---:|---:|---:|---:|---:|
| decode c=1 | 78.7 | 49.7 | 68.8 | **96.3** | 39.5 |
| agg c=8 | 184.4 | **232.1** | 152.8 | 185.1 | 136.2 |
| agg c=16 | 205.5 | **364.7** | n/a | 225.7 | — |
| max ctx | 131k | 131k | **32k only** | 131k | 131k |
| free VRAM | **10.5G** | 3.6G | 0.5G | 2.0G | 2.5G |
| fact extraction | **15/15** | **15/15** | **15/15** | intermittent 500s | **0/15** |
| consolidation (prod) | **5/5** | 1/5 | **5/5** | fails | 0/5 |

### Dense beats MoE on aggregate — the opposite of the usual intuition

Only the **fully dense** 12B amortizes one weight read across a whole batch. E4B
(MatFormer selective activation), 26B-A4B (MoE) and gpt-oss (MoE) all have concurrent
streams touching *different* sub-networks, so they scale worse under load even when they
win single-stream. gpt-oss is fastest at c=1 (96.3) yet the 12B beats it by **62%** at 16
streams (364.7 vs 225.7). **Never pick a model for a concurrent workload on a
single-stream benchmark.**

### Verbosity × speed is a real disqualifier

Consolidation is one long generation racing Hindsight's 120s timeout. gemma-4-12b-qat
needs ~5563 completion tokens for a batch that costs gpt-oss ~825–938; at 49.7 tok/s
that is ~112s, and it **timed out 4/5** at production settings. E4B does the same work
inside a 2500-token cap (5/5 both capped and uncapped). Hindsight sends **no**
`max_completion_tokens` for lmstudio, so nothing caps a verbose model — only wall-clock.

### Harness traps that produced wrong answers before being caught

- **Strip think tags.** A probe scoring 0/10 *both with and without* `json_schema` is a
  broken harness, not a broken model — that symmetry is the tell. Hindsight's provider
  strips `<think>/<thinking>/<thought>/<reasoning>`; a naive probe stripping only
  markdown fences scores every thinking model at zero.
- **Check `finish_reason=length` before blaming a model.** Both Gemmas "failed"
  consolidation 0/5 purely because the harness capped at 2500 tokens.
- Qwen3.5-9B's failure is real and different: it spends the whole budget reasoning
  (2000/2000 tokens, **empty** content; needs 2760 to answer at all, 771 with
  `/no_think`). A thinking model is a poor fit for per-turn extraction.

### Caveat

Every score above is **schema validity, not extraction quality**. A 4B-effective model
can emit perfectly valid JSON containing mediocre facts, and for long-term memory a
confidently-wrong memory is worse than a failure. Compare *what facts are actually
extracted* before committing to E4B on these numbers alone.

## Extraction QUALITY eval (2026-08-02) — not just schema validity

Throughput and schema-compliance say nothing about whether the *facts* are right. Ran 8
adversarial scenarios through Hindsight's real `dry-run-extract` endpoint (production
retain path, no persistence) against the `astra-personal` bank.

| # | scenario | gemma-4-E4B-it-qat | gemma-4-12b-it-qat |
|---|---|---|---|
| 1 | durable pref vs transient status | pass | pass |
| 2 | credentials (must not store) | pass | pass |
| 3 | two-person attribution (Josh/Gina) | pass | pass |
| 4 | home infrastructure | pass (2 facts) | pass (merged to 1) |
| 5 | relative date resolution | **WRONG DATE** | **TIMEOUT (4 attempts)** |
| 6 | contradiction / supersession | pass | pass |
| 7 | hallucination bait (vague input) | **pass — extracted nothing** | **pass — extracted nothing** |
| 8 | one-off progress log | **pass — extracted nothing** | **pass — extracted nothing** |

### The finding that dominated everything: a config bug, not a model deficiency

`astra-personal` had **`mission: ""` and `retain_mission: null`**, and the Hermes plugin
reads `bank_retain_mission` from `~/.hermes/hindsight/config.json` into
`_bank_retain_mission` (`plugins/memory/hindsight/__init__.py:713, 1309`) and **never uses
it**. So extraction ran with NO guardrails. Same input, mission off vs on:

- credentials: stored `password Hunter2Winter!` **and indexed it as a searchable entity**
  → with mission, password dropped, useful facts kept
- transient: stored "the Hindsight rebuild is ~80% complete"
  → with mission, dropped

Fixed by `PATCH /v1/default/banks/astra-personal/config` with
`{"updates": {"retain_mission": ...}}` — applies to every client regardless of the plugin
bug. Verified with no per-request override. **Audit of the existing 13,461 facts found no
real leaked secrets** (37 regex hits were all *discussions about* credentials), but that was
luck, not the guardrail working.

### Model-specific defects

- **E4B: date arithmetic is wrong.** Reference Sunday 2026-08-02, "next Tuesday" →
  answered **Aug 3, a Monday** (correct: Aug 4). Silent, confident, schema-valid, and it
  propagates into `event_date`/`occurred_start`. Verify before trusting dated events.
- **12B: thinks itself out of the time budget.** ~1899 thinking tokens/extraction vs E4B's
  ~505, at 63% the decode speed — ~6x slower per call. It **timed out 4/4 attempts** on
  case 5 and 4/5 on consolidation. Its verbosity is the disqualifier, not its judgment.

### Both models refuse to invent — the best result here

Cases 7 and 8 were the ones worth worrying about. Given *"That thing we discussed didn't
work out, so I went the other way"* both returned **zero facts**. A model that knows when
NOT to write to memory beats one that extracts aggressively; every spurious fact pollutes
recall permanently.

### Caveats on these numbers

8 synthetic cases characterize *error classes*, not a pass rate. `retain_extraction_mode`
is `concise` on this bank, which shapes verbosity independently of model choice.

## Baseline check vs the model actually in production: gpt-oss-120b (OpenRouter)

Hindsight had been running `openai/gpt-oss-120b` via `https://openrouter.ai/api/v1`. Ran the
SAME 8 scenarios against it, same bank, same `retain_mission`, so "are we degrading quality
by going local?" gets an evidence-based answer rather than an assumption.

| # | scenario | E4B (local, 3.9G) | 12B-QAT (local) | **gpt-oss-120b (hosted)** |
|---|---|---|---|---|
| 1 | durable pref vs transient | pass | pass | **FAIL — kept "rebuild ~80% complete"** |
| 2 | credentials | pass | pass | pass |
| 3 | two-person attribution | pass | pass | pass |
| 4 | home infrastructure | pass | pass | pass |
| 5 | relative date | **FAIL — Aug 3 (Mon)** | FAIL — timeout | **pass — Aug 4, correct** |
| 6 | contradiction / supersession | pass | pass | pass |
| 7 | hallucination bait | **pass — nothing** | pass — nothing | **FAIL — vacuous fact** |
| 8 | one-off progress log | **pass — nothing** | pass — nothing | **FAIL — stored the log** |
| | **score** | **7/8** | 6/8 | **5/8** |

### The 120B is not better for this workload — it is more *extractive*

Every 120B failure is over-extraction: it captures more, including exactly the categories the
retain mission excludes. On the hallucination bait it manufactured a content-free fact
("Josh's previously discussed plan failed, so he chose an alternative approach"), and it stored
the one-off deploy log verbatim. E4B refused both. Bigger model, looser mission adherence.

Its one clear win is **date arithmetic** — the case E4B got wrong (Aug 4 vs E4B's Aug 3) and
the 12B timed out on. Mitigation is upstream: have Hermes resolve relative dates to absolute
before retain, rather than asking the model to do calendar math.

### Implication worth chasing

If the 120B over-extracts transient content, the existing 13,461-fact bank may be carrying a
lot of one-off noise (deploy logs, progress updates) accumulated under the *previous* provider
AND without any retain_mission. Worth auditing fact-type distribution before assuming the bank
is all durable signal.

### Caveats

8 short synthetic cases characterize error CLASSES, not pass rates, and short inputs may
understate a large model's advantage on long, tangled real conversations. Consolidation quality
was not compared across providers, only extraction.

## HARDER eval (12 realistic multi-turn conversations) — reverses the short-set result

The 8 short cases said local E4B >= gpt-oss-120b. That did not survive harder inputs.
12 cases with multi-turn conversations, cross-turn reference, hypotheticals, sarcasm and
ambiguous pronouns, each with explicit expect/avoid lists.

| case | gpt-oss-120b | gemma-4-E4B-it-qat | better |
|---|---|---|---|
| H1 durable buried in chatter | 500 error | rule+trip ok, +UPS noise | — |
| H2 contradiction across turns | pass | pass | tie |
| H3 hypothetical | 2 facts incl "not planning in 2026" | "Josh REQUIRES a mini-split" — no hedge | 120b |
| H4 negation | pass | pass | tie |
| H5 third-party attribution | pass | pass | tie |
| H6 credentials in tech block | pw dropped, kept node addr + key name | pw dropped, lost useful context | 120b |
| H7 quantities | pass | pass | tie |
| H8 recurring vs one-time | habit + transient noise | habit only | **E4B** |
| H9 sarcasm | clean | stored "ironic affection for the printer" | 120b |
| H10 ambiguous pronouns | binding ok + push/hold decision | binding ok, MISSED the decision | 120b |
| H11 self-correction | "the 21st of the month" | "**August** 21st" — INVENTED the month | 120b |
| H12 operational noise | stored all 4 avoided items | **nothing** | **E4B** |

**120b wins 5, E4B wins 2, 4 ties.**

### The two models fail in different, non-symmetric ways

- **120b = capable but undisciplined.** Every failure is over-extraction (H12 stored the whole
  deploy log, H3 dropped the hedge partially, H8 added transient status). Junk is filterable,
  and the retain_mission that was missing for this bank's whole life is now set.
- **E4B = disciplined but invents.** H11 turned "the 21st" into "August 21st" — the same class
  as its earlier "next Tuesday -> Monday" error: silent, confident, schema-valid, WRONG. It also
  drops signal (H10 lost the actionable push/hold decision, H6 lost node context).

For a long-term memory bank, weight these asymmetrically: **junk can be filtered later,
fabricated facts cannot be distinguished from real ones after the fact.**

### Method note

The short 8-case set produced the OPPOSITE ranking. Short probes flatter small models because
they never require cross-turn reference resolution or figurative-language handling. Do not
conclude a model is adequate for extraction from short synthetic snippets.
