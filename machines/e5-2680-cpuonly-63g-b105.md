## Notes

**The first CPU-only box in this repo** — no GPU of any kind, so every row is pure CPU with no
hybrid-offload contribution. Served by **llama.cpp `llama-server`** (`c8e03ce`) rather than LM
Studio, via `bench.py --api llamacpp`. An otherwise-idle 2U dual-socket server with 1 of 2
sockets populated.

### Memory architecture (the number that governs everything else)

8× 8 GB DDR4-**2666** single-rank RDIMMs, **2 in each of the 4 channels** — evenly balanced.
BIOS clocks them to **2400 MT/s** because Broadwell-EP's memory controller caps there: *the DIMMs
are faster than any CPU this socket accepts*, so the 2666 premium was wasted and no BIOS tuning
recovers it.

| | |
|---|---|
| theoretical | 4 × 2400 × 8 B = **76.8 GB/s** |
| **measured (STREAM Triad)** | **48.0 GB/s** = **62.5%** of theoretical |
| by threads | 11.6 / 36.0 / 46.1 / **48.0** / 46.3 at 1/4/8/14/28 |

Bandwidth saturates at ~8 threads, and **28 threads (hyperthreading) regresses** — independently
reproducing this repo's "threads = physical cores" rule on a third architecture.

### ⭐ Headline: the quant curve depends on the MODEL, not the box

Both measured here, same engine, same day:

| model | Q4 | Q5 | Q6 | Q8 | Q4→Q8 |
|---|---:|---:|---:|---:|---:|
| Qwen3.6-35B-A3B (MoE, ~3B active) | 13.02 | 12.24 | 11.86 | **11.41** | **1.14×** |
| Gemma-4-E4B (dense-ish, 7.5B) | 15.29 | 11.92 | 11.14 | **9.57** | **1.60×** |

Bytes ratio across that range is ~1.70×. The dense model tracks it (**bandwidth-bound**); the MoE
does not (**latency-bound** — it reads only its active experts, a scattered gather-heavy pattern
that can't saturate the bus, so the serial per-layer chain dominates).

**Consequence worth internalising: at Q8 the 35B MoE (11.41) is 19% FASTER than the 7.5B dense
(9.57).** Five times the parameters, and quicker. Don't downsize a model to chase CPU speed.

### Recommended config

- **Interactive, MoE:** Q8_K_XL, `-np 1`, `--spec-type draft-mtp --spec-draft-n-max 1`, `-t 14`,
  f16 KV, **flash-attn off**.
- **Serving, MoE:** same but **MTP off** and `-np 4` — MTP costs −18% aggregate at 4 streams.
- **Gemma/dense:** best MTP depth is **4**, not 1, and flash-attn **on** is slightly better.
  Neither model's tuning transfers to the other.

### Things that surprised me

- **Flash attention is 5.9% SLOWER on CPU** (13.41 off vs 12.66 on, f16 KV both sides). The
  "flash attn on" guidance in the README is GPU-derived and inverts here.
- **Context allocation is free** — 12.99/13.02/12.95 at 4k/32k/128k. (Caveat: the decode prompt is
  short, so this measures *allocation*, not decode at genuine 128k depth.)
- **Concurrency scales**: aggregate 13.3 → 21.6 → 32.4 at 1/2/4 streams (MoE), 15.5 → 41.4 at 1→8
  (dense). A CPU-only box **can** serve multiple users — unlike a bandwidth-saturated hybrid,
  where aggregate is capped at the single-stream number.
- **MTP depth 6 is slower than MTP off** on both models. Acceptance decays hard with depth.
- **The MTP multiplier depends on output length** — 1.50× at 128 tokens vs 1.16× at 256, same box
  and config, because acceptance decays through a generation. **Record `max_tokens` with any MTP
  figure**, or it isn't comparable across machines.
- **Prefill is the weak axis**: ~65 tok/s, ~21 s to ingest 2k tokens, essentially quant-independent
  (Broadwell has AVX2 but no AVX-512). On this class of box a cheap GPU is better justified as a
  *prefill* accelerator than for decode offload.

### Gotcha for anyone reproducing this

`--draft-max` / `--draft-min` were **removed** upstream in favour of `--spec-draft-n-max` /
`--spec-draft-n-min`. Passing the old name makes `llama-server` exit during **argument parsing**,
which inside a sweep is indistinguishable from a failed model load. Cost me a whole MTP pass.

### Contrast with the f732 GPU box

`f732` recorded (2026-08-05) that **MTP regressed into a ~14% loss** on this same model after a
2026-07-14 runtime change — acceptance went *up* while throughput went *down*, i.e. the verify
path got more expensive. **This box shows the opposite: MTP is a solid win** (1.26× on the MoE,
1.39× on Gemma).

The two aren't in conflict; they're different engines and different regimes — `f732` is LM Studio
on a VRAM-resident GPU, this is stock `llama.cpp` on CPU. Together they make the point that
**MTP's value is not a property of the model**: it depends on engine version, hardware regime,
draft depth, concurrency, and output length, every one of which moved it materially here. Measure
it per box after any runtime upgrade rather than assuming a multiplier.
